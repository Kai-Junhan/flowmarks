# FlowMarks 代码链路书签生成

把用户指定的一个代码流程整理成 FlowMarks 可导入的书签候选。插件不运行 AI；它只负责读取候选、展示书签和跳转代码。

## 不可违反的规则

1. 先验证锚点，再向用户展示方案。行号必须来自实际文件，不能凭记忆或估算。
2. 一次只处理一个工作流。创建、运行时处理、设备绑定、缓存、入库属于不同工作流，除非用户明确要求合并，否则必须拆开。
3. 讨论阶段不创建、不修改任何文件。只有用户明确回复“确认生成”或同义确认后才写入。
4. 行为结论必须有代码证据。缓存、权限、数据库约束、默认值等结论必须读对应实现和 SQL，不能从方法名推断。
5. 只操作当前项目根目录，不跨项目读取或写入 `.flowmarks`。
6. 不修改业务源代码，不写 `.flowmarks.json`，不自动导入书签。

## 第一阶段：讨论，不写文件

### 1. 先确定工作流边界

用一句话写清楚用户真正要完成的事，例如“通过创建接口写入一条接入物模型”。

只收录完成这件事必需的节点。以“写创建脚本”为例，创建链路通常是：

类/请求对象 → 接口入口 → 参数与协议校验 → 权限/项目归属 → 编码或业务唯一性 → 服务层默认值 → 数据写入

以下内容默认属于另一个工作流，不要混进创建分组：

- 设备上报后的运行时分流
- 模型缓存和刷新
- 设备类型绑定
- JS 沙箱执行
- 数据入库/去重

默认 5–8 条。超过 8 条时必须拆组，或在方案中说明为什么不能拆；不要用一个“大而全”的分组代替边界判断。

### 2. 逐条验证锚点

对每个候选节点执行以下检查：

- 用 `rg -n` 或直接读取文件定位目标声明/语句。
- 以文件真实行号为准，不沿用搜索结果之外的估算行号。
- 读回该行并与 `expectedLineText` 逐字比较，只去掉行首行尾空白。
- 类声明必须指向 `public class ...` 本身，不能指向注释、注解或字段声明。
- 方法声明必须指向方法签名，不能指向 `@PostMapping` 等注解行。
- XML/SQL 优先指向真正的 `insert/update/select` 语句或关键字段，不选 `<resultMap>` 开头这类弱锚点。
- 如果同一行文本在文件中出现多次，继续读上下文；无法唯一定位时明确标注不确定。

在讨论阶段也必须先做一次上述验证，而不是等到写文件时再检查。

向用户展示方案时使用可核对的形式：

| 步骤 | 标题 | 文件:行 | 已验证 |
|---|---|---|---|
| 1 | ... | `path/File.java:13` | 是 |

不确定的条目写“待确认”，不要伪装成已验证。

### 3. 行为结论必须有证据

只有代码能证明的行为才能写进方案：

- 说“没有调用 refresh”前，同时检查写路径和读路径，确认缓存到底用于路由还是数据读取。
- 说“权限校验会跳过”前，读权限实现和调用条件，确认 null/空值时的真实行为。
- 说“数据库会兜底”前，读建表 SQL 和 Mapper，区分 NOT NULL、唯一键和业务查重。
- 不要把 TODO、缺口或推测混进书签；需要提及时，单独放在“风险与缺口”，并标注证据位置。

如果无法证明，写“未验证”，不要下结论。

### 4. 写操作脚本专项检查

用户要写创建/修改脚本时，额外确认：

- 哪些字段是必填，哪些由服务端补默认值。
- 项目归属、`deptId` 等字段为 null 时，权限检查是否会失效。
- 唯一性检查是全局还是按项目/租户。
- 数据库是否有 NOT NULL、唯一键或其他约束。
- 创建/编辑后是否需要刷新缓存、版本或状态字段。

只写已验证的事实。讨论结束后，等待用户明确确认。

## 第二阶段：确认后生成

用户确认后：

1. 重新读取每个锚点，行号和 `expectedLineText` 必须与当前代码一致。
2. 路径必须是当前项目根目录下的相对路径，禁止绝对路径、`..` 和项目外路径。
3. 一个工作流使用一个分组，按执行顺序排列。
4. 写入当前项目的 `.flowmarks/inbox/<workflow-slug>.json`；目录不存在时创建。
5. 不覆盖已有候选；文件名冲突时使用带序号的新文件名。
6. 优先运行仓库内的校验脚本：

   ```text
   python .agents/skills/flowmarks-bookmarks/scripts/validate_candidate.py <项目根目录> <候选文件>
   ```

   脚本会检查路径边界、文件是否存在、行号范围以及 `expectedLineText` 是否与该行一致。任何错误都必须修正；不要带着校验错误交付。

7. 再次读取 JSON，确认语法、字段和分组数量。
8. 回复候选文件的绝对路径、分组名、条目数量和简短摘要。

不要声称已经导入。导入由用户在 FlowMarks 中完成。

## 输出格式

~~~json
{
  "version": 1,
  "groups": [
    {
      "name": "登录处理链路",
      "items": [
        {
          "title": "接收登录请求并校验参数",
          "filePath": "src/main/java/example/LoginController.java",
          "line": 42,
          "expectedLineText": "public LoginResult login(LoginRequest request) {",
          "step": "1",
          "level": 0
        }
      ]
    }
  ]
}
~~~

插件也兼容 BookmarkAI 的 `targetGroupName` + `items` 格式，但新文件一律使用标准格式。

`step` 和 `level` 是可选字段：主步骤用 `1、2、3` 且 `level=0`；子步骤用 `2.1、2.2` 且 `level=1`。旧候选没有这两个字段时仍然兼容。

## 项目隔离

- 每个项目只拥有自己的 `.flowmarks.json`、`.flowmarks/inbox/` 和 `.flowmarks/archive/`。
- 不同项目即使分组同名，也不能合并或复用书签。
- 书签路径始终相对于所属项目根目录解析。
- 分析另一个项目前先确认工作目录已经切换，不能把两个项目的书签写入同一个目录。

## 回复格式：简洁优先

讨论阶段的回复只保留以下内容，默认不超过 20 行正文：

1. 一句话结论：这是什么链路、准备生成几条书签。
2. 一张锚点表，5–8 行，列为：`步骤 | 标题 | 文件:行 | 已验证`。
3. “关键约束”最多 5 条，每条一行；只写会影响脚本或使用的结论。
4. 最后一句：请用户回复“确认生成”或提出修改。

不要重复大段代码，不要复述文件内容，不要写背景介绍，不要把所有缺口都展开。发现错误时只列：

```text
1. 问题：... 修正：...
2. 问题：... 修正：...
```

生成后的回复只包含：候选文件路径、分组名、书签数量、校验脚本结果、下一步操作。不要把 JSON 全文贴回来。

## 交付前自检

- [ ] 每个行号都已读回文件核对，`expectedLineText` 与目标行完全一致。
- [ ] 一个分组只覆盖一个工作流，默认不超过 8 条。
- [ ] 有子步骤时使用 `2.1/2.2` 和 `level=1`，编号与顺序一致。
- [ ] 没有把运行时、缓存、绑定、入库混入创建链路。
- [ ] 没有未经验证的缓存、权限或数据库结论。
- [ ] 路径全部位于当前项目内。
- [ ] 讨论阶段没有写文件；生成后校验脚本通过。
